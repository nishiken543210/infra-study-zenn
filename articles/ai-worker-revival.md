前回の記事では、業務インフラ経験者がホームラボで気づいた「知識の穴」の話を書きました。

今回は「インフラを作る話」ではなく、**作業中に過去の実装を掘り起こして再利用した話**です。

---

## 各章に「使えない」AIボタンがあった

自宅ホームラボで制作中の Linux 学習プラットフォームの各章ページには、ずっとこんな UI がありました。

```
[AI に相談（v2 公開予定）]
```

グレーアウトされた disabled なボタンです。クリックしても何も起きない。「いつか動かす予定」としてずっと放置していました。

これをそろそろ動かそう、という話になりました。

---

## 最初の思い込み：新規で Pages Functions を作るつもりだった

Cloudflare Pages でホストしている静的サイトに AI を繋ぐとなると、こういう流れかなと頭に浮かびました：

1. Cloudflare Pages Functions を新規作成する
2. Workers AI の binding を設定する
3. `node` と `wrangler` のバージョンを確認して……

「静的サイトにサーバーサイドの機能を追加するなら、Functions を書くのが筋だろう」という思い込みです。

作業を始めようとした、そのタイミングで気づきました。

---

## 「あれ、前に AI 使えてた気がする」

ふと、記憶が浮かんできました。

*以前このサイトで AI 相談を使えていた。どこかに実装があったはず。*

はっきりとした記憶ではないですが、確かに動いていた感覚があった。だったら新規で作る前に、まず確認してみようと思いました。

---

## git log -S で過去を掘り起こす

Claude Code（AI エージェント）に調べてもらいました。git の差分検索オプション `-S` を使うと、指定した文字列が「追加または削除されたコミット」を絞り込めます。

```bash
git log --oneline -S "env.AI"
```

結果が出てきました。

```
0e25162 ClaudeFlereAI導入
1077e2a ClaudeFlereAI導入2
```

コミットメッセージが若干雑ですが（自分で打ったやつです）、確かにある。

---

## test_iframe.html に全部入っていた

該当のコミットを掘ってみると、`test_iframe.html` というファイルが出てきました。

中身を見ると——

- Worker の URL: `https://infra-study-ai.[your-account].workers.dev`
- リクエスト形式: `POST` で `{question, lesson}` を送る
- レスポンス形式: `{answer}` が返ってくる
- CORS: `*` で全開放

シンプルな構成で fetch 一発で叩けます。

しかも、この Worker は **既にデプロイ済みで稼働中** でした。

---

## curl で叩いたら、即答が返ってきた

試しに叩いてみます。

```bash
curl -X POST https://infra-study-ai.[your-account].workers.dev \
  -H "Content-Type: application/json" \
  -d '{"question": "ls コマンドは何をするコマンドですか？", "lesson": "ch1"}'
```

数秒後、日本語の回答が返ってきました。

**新規インフラ構築ゼロ。** Worker はとっくに動いていた。

「Pages Functions を新規作成して……」と考え始めていた自分は、完全に空回りしていました。

---

## 実装：disabled を fetch 配線に差し替えるだけ

インフラ側は何もしなくていい。変えるのは HTML と CSS だけです。

各章にあった mock UI——disabled の input と button——を、実際に fetch を呼ぶロジックに差し替えます。

Ch1 で動作確認を取ってから、Ch2〜8 に一括展開しました。変更は HTML と CSS のみ。Worker 側にもサーバー設定にも手を加えていません。

「フロントを繋ぎ直す」だけで完了しました。

---

## デプロイは git push 一発だった

もうひとつ、このタイミングで確認できたことがあります。

`git push` を打つと——Cloudflare Pages が自動ビルドを走らせて、`infra-study.pages.dev` に反映される。

CI/CD として当然の話なのですが、このプロジェクトでは「本当に push だけでいいのか」「デプロイ経路がどこか」が長らく曖昧なままでした。実際に push して反映を確認し、**この一本道がはっきりしました**。

---

## git log -S を知っているかどうかで、調査の深さが変わる

`git log -S` はインフラエンジニアが意外と知らないオプションです。

`grep` でコードを検索するのと違い、「そのコードが消えたり追加されたりしたコミット」を探せます。

- 「この設定、昔は違ったはずだけど、いつ変わったんだっけ」
- 「前のバージョンの実装がどこかに残っているはず」

こういうときに使えます。git 履歴は、プロジェクトの記憶です。コードを書く前に、まず履歴を掘ってみる——という習慣は案外大事だと再確認しました。

---

## まとめ

- 各章の disabled だった AI UI が、今日動くようになった
- 「新規構築が必要」と思い込む前に、既存の実装を確認するのが先
- `git log -S "文字列"` で、過去の実装を文字列検索で掘り起こせる
- 自分でコミットしたものが宝になることがある
