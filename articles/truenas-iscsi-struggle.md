前回の記事では、HPE ML30 に Proxmox を入れて最初の仮想マシンが動いた話を書きました。

今回はその次のステップ——**TrueNAS でストレージを作って、iSCSI で他の VM に繋げるまで**の話です。かなり詰まったので、失敗談として正直に書きます。

---

## そもそも iSCSI って何なのか

まず、知らない人のために少しだけ説明します（自分も最初は知りませんでした）。

**iSCSI（アイスカジー）** は、ネットワーク越しにストレージを使うための仕組みです。「IP ネットワーク上で SCSI のディスクを使う」というのが元々の意味で、要は「別のサーバーにあるディスクを、まるで自分の内蔵ディスクのように使える」技術です。

物理的には1台の TrueNAS に大容量ディスクをまとめておいて、Proxmox の各 VM には「ネットワーク越しにここを使え」と指示する。こうすることで、ディスクの管理を1か所に集中できます。

登場人物は2つ。

- **Target（ターゲット）**: ストレージを提供する側。今回は TrueNAS
- **Initiator（イニシエーター）**: ストレージを使う側。今回は Proxmox の VM

この2つが会話して、「ここのディスクを使っていいよ」「わかった、繋ぐね」というやりとりをするのが iSCSI の基本的な流れです。

---

## TrueNAS の VM を立てた

Proxmox の管理画面から、TrueNAS の VM を作りました。

TrueNAS は ZFS というファイルシステムを使ったストレージ管理の OSS で、ホームラボでの人気がとても高い。ドキュメントも充実しているし、Web UI も洗練されています。「これなら簡単にできそう」と思っていました。

VM を起動して、ブラウザから TrueNAS の管理画面を開く。ストレージのプールを作って、iSCSI の設定を入れていく——

*「あれ、繋がらない」*

---

## discoverydb のエラーで詰まる

iSCSI を使うとき、Initiator 側（VM）はまず **Discovery（探索）** という作業をします。「このネットワーク上に iSCSI の Target はいますか？」と問い合わせる仕組みです。

Linux の VM から試してみると、`iscsiadm` コマンドで discoverydb（探索のデータベース）に関するエラーが返ってくる。

```
iscsiadm: Could not connect to iscsid: No such file or directory
iscsiadm: initiatorname configuration error...
```

「データベース？ iscsid？ initiatorname？」——コマンド1本打っただけで、知らない単語が3つ出てきました。

原因を調べていくと、`open-iscsi` パッケージが入っていないとか、`iscsid` サービスが起動していないとか、`/etc/iscsi/initiatorname.iscsi` のファイルが正しく設定されていないとか——複数の「前提条件」がいくつも重なっていました。

---

## Portal と IQN の話

次にぶつかったのが **IQN（iSCSI Qualified Name）** という概念です。

iSCSI の世界では、Target を識別するために名前をつけます。それが IQN で、こんな形式になっています。

```
iqn.2005-10.org.freenas.ctl:extent-lun0
```

最初見たとき「なんだこれ」と思いました。

分解すると、`iqn.` + 年月 + ドメイン名（逆順）+ コロン + 識別子、という構造になっている。TrueNAS が自動で生成してくれるのですが、この文字列を Initiator 側にも正確に指定しないと Target を見つけられません。

**Portal** というのも出てきます。これは「どの IP アドレス・ポートで iSCSI の接続を受け付けるか」を定義するもの。

うちの TrueNAS は `10.10.10.10:3260` というアドレスで待ち受けていました。これは Proxmox 内の管理用ネットワーク（vmbr1）専用の IP で、外からは直接見えない設計になっています。ということは、接続する VM もこのネットワーク（10.10.10.0/24）に参加していないといけない。

「あ、VM にネットワークインターフェースが足りない」

---

## NAA 値という謎

接続できるようになったと思ったら、今度は **NAA 値** という言葉が出てきました。

NAA は「Name Address Authority」の略で、ストレージデバイスを世界で一意に識別するための番号です。`/dev/disk/by-id/` 以下に `wwn-0x...` という形で現れます。

Proxmox が iSCSI の LUN を認識すると、この NAA 値でディスクを識別しようとします。「ディスクが見えているのに、Proxmox が認識しない」という状態になったとき、この NAA 値の不一致が原因のことがありました。

ストレージの世界は、「繋がる」と「使える」の間に、意外と距離があります。

---

## オチ：「実はもう動いていた」

いろいろ調べて、設定を追いかけて——数時間格闘した末に気づいたことがあります。

**TrueNAS の iSCSI は、最初から正しく設定されていた。**

ZFS のプール、zvol（仮想ディスク）、Portal、Target、Extent——すべて既存の設定で正常に動いていました。問題は TrueNAS 側ではなく、**接続する VM 側の準備が足りていなかった**だけだったんです。

- `open-iscsi` パッケージが未インストール
- `iscsid` サービスが未起動
- VM に iSCSI ネットワーク用の NIC が未追加

つまり、ドアは最初から開いていた。入ろうとしている側の鍵（準備）ができていなかっただけ。

「……あ、そういうことか」

インフラの問題は、意外とこういうオチが多い。「サーバーが壊れた」と思って調べ続けたら「LANケーブルが抜けていた」みたいな話と、構造は同じです。

---

## 開通したときのこと

VM に NIC を追加して、`open-iscsi` をインストールして、`iscsiadm` で探索をかけると——ターゲットが見えた。

```
10.10.10.10:3260,1 iqn.2005-10.org.freenas.ctl:extent-lun0
```

ログインして、`lsblk` でディスク一覧を見ると、新しいデバイスが追加されている。`/dev/sdb` が現れていた。

「繋がった。」

地味なコマンドの出力ですが、「ネットワーク越しに別の筐体にあるディスクが、自分の VM の /dev に現れている」という状況は、なかなか不思議な感覚です。物理でやっているから余計にそう思うのかもしれません。

---

## この経験から学んだこと

詰まっていたとき、「TrueNAS の設定が悪いんじゃないか」「Proxmox の何かがおかしいんじゃないか」とばかり考えていました。

でも実際は、問題は接続する側の「前提条件の欠如」でした。

インフラのトラブルシュートで大事なのは、**問題の切り分け**です。「Target 側は正常か」「Initiator 側は正常か」「ネットワークは通っているか」——この3層を順番に確認する。それだけのことなのですが、わからない状態だと「どこを見ればいいか」自体がわからないので、全部が怪しく見えてしまいます。

ひとつ詰まるたびに、「次は同じところで詰まらないぞ」と思う。それがホームラボの積み重ね方なんだと思っています。

---

## 現在の構成

今は TrueNAS の iSCSI を使って、Proxmox のストレージとして 100GB の LUN を提供しています。

```
TrueNAS VM (10.10.10.10)
  └── ZFS pool: datapool1
       └── zvol: zvol-lun0 (100GB)
            └── iSCSI Target → Proxmox がストレージとして認識
```

この構成が安定したことで、「VM のディスクをどこに置くか」を柔軟に管理できるようになりました。

---

## まとめ

- iSCSI は「ネットワーク越しにディスクを使う」仕組み。Target（提供側）と Initiator（使う側）がいる
- TrueNAS 側は最初から正しく設定されていた——問題は VM 側の準備不足だった
- `open-iscsi` の未インストール・NIC の未追加・ネットワークの不参加、の3点が原因
- 「繋がらない」原因は、意外と自分の側にあることが多い
- トラブルシュートは「どの層に問題があるか」を切り分けることが先決
