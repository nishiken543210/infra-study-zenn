前回の記事では、このプラットフォームの全体構成——1台の物理サーバーにどれだけのことを詰め込んでいるか——を整理しました。

今回は「その物理サーバー、電源どうしてるの？」という話です。

---

## 電気代の話から始まった

自宅サーバーを年中つけっぱなしにすると、電気代が地味にきつい。

HPE ML30 は学習用サーバーとしては小さい部類ですが、それでも常時稼働させると月の電気代がじわじわ乗ってくる。「使わないときは落としておこう」という判断は自然でした。

問題は、「落とすと遠隔から起こせなくなる」ことです。

電源がオフの状態では、SSH も届かない。Proxmox の管理画面にもアクセスできない。「サーバーが起きていないと何もできない」という当たり前の壁にぶつかりました。

これを解決しないと、将来の予約連動の自動起動も実現できない。**「受講予約が入ったら、無人でサーバーを叩き起こす」** ——そのための仕組みが必要でした。

---

## この記事で分かること

- 拡張NICでWoLしようとしたら、ポートによって能力が違った実機の罠

## まず、Wake-on-LAN とは何か

**Wake-on-LAN（WoL）** は、電源オフの状態のマシンをネットワーク経由で起動する仕組みです。

電源を完全に落とした状態でも、NIC（ネットワークインターフェースカード）だけはわずかな待機電力を受け取っています。その NIC が特定のパターンのパケット（マジックパケット）を受信すると、「起動してよい」と判断して電源を投入します。

マジックパケットは「`FF:FF:FF:FF:FF:FF`（6バイトの0xFF）に続いて、宛先MACアドレスを16回繰り返す」という構造を持つUDPパケットです。受信側は電源オフでも、この特定のパターンを検知して電源を入れます。

前提条件は2つあります。

1. **BIOS/UEFI でWoLが有効になっていること**
2. **OSが起動するたびにNICのWoL設定が維持されること**

この2点を確認・設定するのが今回の作業の骨格です。

---

## 設定の流れ

### BIOS を確認する

ML30 には iLO（Integrated Lights-Out）という遠隔管理機能があります。ブラウザから iLO の管理画面にアクセスして、仮想コンソールを使えば、サーバーが起動していない状態でも BIOS の設定を確認・変更できます。

確認場所は `System Utilities → システムオプション → サーバ可用性 → ウェイクオン LAN` です。

結果は「**既に有効**」でした。ML30 はデフォルトで WoL がオンになっていたため、BIOS 側の変更は不要でした。

### OS側のWoL設定を確認する

次に、Proxmox ホストに SSH でログインして NIC の状態を確認します。

```bash
ethtool nic0 | grep Wake
```

出力はこうでした。

```
        Supports Wake-on: g
        Wake-on: g
```

`g` は「マジックパケットでの WoL に対応している」という意味です。`Wake-on: g` がすでに有効になっていました。

nic0 のドライバは `tg3`（Broadcom BCM5720）です。これが今回の主役の NIC です。

### 永続化する

ここに落とし穴があります。`ethtool` で設定した WoL の状態は、**デフォルトではシャットダウン後に失われます**。再起動するたびに WoL が無効に戻るサーバーは、実用にならない。

これを防ぐために、systemd の oneshot サービスを作成します。

```
/etc/systemd/system/wol-nic0.service
```

起動するたびに `ethtool -s nic0 wol g` を実行し、WoL を有効な状態に戻す仕組みです。`systemctl enable --now wol-nic0.service` で有効化・即時起動し、`is-enabled` と `is-active` で確認しました。

### 送信元を準備する

WoL のマジックパケットを送る役割は、**常時稼働の Raspberry Pi 3B+** に担わせます。

このラズパイはもともと Cloudflare Tunnel のエージェントとして常時稼働していました。ML30 が寝ているときでも、ラズパイは動き続けている。同じ自宅 LAN に繋がっているラズパイからマジックパケットを送れば、ML30 を叩き起こせます。

ラズパイに `wakeonlan` コマンドを入れて、起動コマンドを確認しました。

```bash
wakeonlan xx:xx:xx:xx:xx:xx
```

（MACアドレスは実機確認済みのものに置き換えます）

### 実地検証

ML30 をシャットダウンして、iLO で電源オフを確認。ラズパイから上記のコマンドを実行。

```
Sending magic packet to 255.255.255.255:9 with xx:xx:xx:xx:xx:xx
```

ping 監視を続けると——**約 85 秒後に ML30 が ping 応答を開始しました。**

電源オフの状態から、マジックパケットだけで起動が完了しました。2回連続で再現を確認して、動作を確定としました。

## ここからが本番——iLO の「罠」

設定が動いてから、オーナーとの会話でひとつ重要な認識の誤りが出てきました。

「iLO があれば、nic0 が壊れても管理できるでしょ？」という話です。

HPE のサーバーには iLO という専用の管理インターフェースがあります。iLO があれば、OSが起動していない状態でもリモートから電源操作や画面確認ができる——**「だから iLO は冗長の保険になる」** という思い込みがありました。

**これは誤りでした。**

ML30 Gen10 の iLO は、**専用の物理 LAN ポートを持ちません**。オンボード NIC（nic0 / Broadcom BCM5720）と **LAN ポートを共用する「Shared NIC」方式**です。

どういうことかというと——nic0 の物理ポート、またはそのチップや配線が故障した場合、**iLO へのネットワーク到達も同時に失われます**。「管理ポートがあるから安心」ではなく、「オンボードNICが生きている限りにおいて管理できる」という条件付きの話でした。

以前、自分の作業メモに「iLO で代替可」と書いていましたが、これは誤りで訂正が必要でした。

---

## Intel I350 でWoL冗長化を試みた結果

「では、別のNICを使って冗長化しよう」という方向になりました。

ML30 には拡張スロットに Intel I350（4ポート）が搭載されています。これなら nic0（Broadcom tg3）とは別チップ・別物理ポートなので、nic0 が壊れても Intel I350 からWoLが送れれば真の冗長になる。

各ポートの状態を `ethtool` で確認しました。

| ポート | 状態 | WoL対応 |
|-------|------|---------|
| ens2f0 | 未配線（ケーブルなし） | 対応（`Supports Wake-on: pumbg`） |
| ens2f1 | vmbr1に接続中（物理ケーブル未接続） | 非対応 |
| ens2f2 | vmbr2に接続中（物理ケーブル未接続） | **非対応（`d`=disable only）** |
| ens2f3 | 未使用 | 非対応 |

**NICならどのポートでもWoLできるわけではありませんでした。**

Intel I350 の場合、ポートによって `Supports Wake-on` の値が違います。`pumbg`（フル対応）のポートもあれば、`d`（WoL機能そのものがdisable専用）のポートもある。同じNICカードの中でも、ポート単位でWoL能力が異なります。

WoL に使えるのは `ens2f0` だけでした。ただしこのポートは未配線——物理ケーブルがまだ刺さっていません。

チップの確認をすると、nic0 が `tg3`（bus 02:00.0）、ens2f* が `igb`（bus 09:00.x）で別系統であることは確認済みです。**`ens2f0` に物理ケーブルを接続すれば、別チップ経由の真の冗長WoLが実現できます。**

ただし、その配線は現在保留中です。ケーブルとスイッチの空きポートの確認が必要で、「動く最小構成を先に確定させる」判断で一旦棚上げにしました。

## 現在の構成と正直な着地

今動いているWoLの構成は以下の通りです。

```
[Raspberry Pi 3B+] ──── [自宅LAN スイッチ] ──── [ML30 nic0（Broadcom tg3）]
  wakeonlan コマンド          同一LAN内              マジックパケット受信 → 電源ON
  (常時稼働)                                         WoL有効・systemd永続化済み
```

**完全な冗長ではありません。** nic0 が壊れたら WoL も iLO も両方届かなくなります。

ただし、「電源オフのML30を無人で起動できる」という当初の目的は達成しました。将来の予約連動自動起動（booking-monitor.py）の前提となる起動経路が成立しています。

「完璧じゃないけど動く」——これが今の正直な状態です。

---

## この経験から言えること

今回の作業で得た教訓を、自分なりに整理します。

**管理ポートは「そのポートが生きている限り」の保険である。**

iLO（IPMI / BMC系全般）は便利ですが、Shared NIC 方式のモデルではオンボードNICの物理障害に対する保険にはなりません。機材を選ぶときに「専用管理ポートか、共有型か」を確認することは重要です。

**NICのWoL能力はポート単位で確認する。**

「Intel I350を持っているからWoLできる」ではなく、「どのポートがWoLに対応しているか」を `ethtool` で実測する必要があります。同一NICカードでもポートによって `Supports Wake-on` の値が異なります。

**「動く最小構成を先に確定させる」は正しい判断だった。**

冗長化を追求するあまり、動作確認を後回しにしてしまうと全体の進行が止まります。今回はまず nic0 で WoL を確定させ、冗長化は物理配線の準備ができたときに対応する——この順序で進めたことで、booking-monitor.py の実装を続けられるようになりました。

---

## 次の一歩

booking-monitor.py の実装は別セッションで完了しています。あとは Google Calendar の Service Account を取得して、ラズパイに配置するだけです。「予約が入ったら自動でML30を起動して、終わったら停止する」という一連の動作が、まもなく全部つながる予定です。

Intel I350 の冗長WoL（`ens2f0` への配線）は、落ち着いたタイミングで対応します。
